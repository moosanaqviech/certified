SQS vs SNS vs EventBridge vs Amazon MQ: Queue, Fan-Out, Router or Broker

Use Amazon SQS to buffer work for one consumer per message, Amazon SNS to push every message to many subscribers, Amazon EventBridge to route events from AWS services, SaaS apps or your code by their content, and Amazon MQ when an existing application already speaks JMS, AMQP or MQTT and must move without code changes.

Last updated October 2026.

What all four give you

Each one lets a producer hand off a message and move on, so a slow or failed consumer does not break the caller. All four are managed and store messages redundantly. They differ in who receives each message, whether delivery is pull or push, whether routing looks inside the message, and which protocols clients use.

Amazon SQS: a queue, one worker per message

Producers send; consumers poll at their own pace and delete a message once it is processed. A visibility timeout hides a received message from other consumers while one works on it. Add consumers to drain the queue faster.

Amazon SNS: publish once, push to every subscriber

A publisher sends to a topic and SNS pushes a copy to every subscription: SQS queues, AWS Lambda, HTTP/S endpoints and Amazon Data Firehose for applications, and SMS, email and mobile push for people. A filter policy on a subscription delivers only the messages it matches. SNS pushes and does not hold messages for a subscriber to fetch later, which is why the classic fan-out pattern puts an SQS queue behind each subscriber: every service gets its own durable copy.

SNS FIFO topics paired with SQS FIFO queues keep order and remove duplicates across the fan-out.

Amazon EventBridge: route events by their content

An event bus takes events from your applications, from SaaS partners and, on the default bus, from AWS services themselves, such as an EC2 state change, with no publishing code. A rule matches an event pattern against any field of the event's JSON and sends matches to its targets. That content-based routing is what SNS topics cannot do.

Two relatives show up in answers: EventBridge Pipes connect one source to one target with filtering and enrichment, and EventBridge Scheduler runs cron, rate or one-time invocations. AWS now recommends Scheduler over the older scheduled rules.

Amazon MQ: a managed broker for existing apps

Amazon MQ runs managed Apache ActiveMQ Classic and RabbitMQ brokers. Because it speaks the industry-standard protocols those brokers use (JMS, AMQP, MQTT, STOMP and others), AWS positions it for migrating existing brokers without rewriting messaging code. For a new cloud-native design, SQS, SNS and EventBridge are serverless and scale without broker sizing, so Amazon MQ is usually the migration answer, not the default.

Signals that decide the question

SQS

"Decouple the web tier from processing", "workers poll", "absorb a traffic spike", "process in order" (FIFO).

SNS plus SQS

"Several systems each need every message", "fan-out", "email or SMS alert", "each subscriber gets a subset".

EventBridge

"React to an AWS service event", "events from a SaaS provider", "route on fields inside the event", "run on a schedule".

Amazon MQ

"Existing application uses JMS, AMQP, MQTT or STOMP", "migrate the on-premises broker without code changes".

The tempting wrong answer: one SQS queue that billing, shipping and analytics all poll. A queue gives each message to one consumer, so the three services would split the orders between them instead of each seeing all of them. That requirement is SNS fan-out to three queues.

FAQ

What is the difference between SQS and SNS?

SQS is a queue: consumers poll it, and each message is processed by one consumer. SNS is a topic: it pushes a copy of every message to all subscribers. Use SNS with an SQS queue per subscriber when several services each need every message.

When should I use EventBridge instead of SNS?

Use EventBridge when events come from AWS services or SaaS partners, or when routing depends on fields inside the event. SNS fits simple fan-out and notifications to people by email, SMS or mobile push.

When should I use Amazon MQ instead of SQS?

Use Amazon MQ when an existing application talks to an ActiveMQ or RabbitMQ broker over JMS, AMQP, MQTT or STOMP and must move to AWS without code changes. For new designs, SQS is serverless and needs no broker to size.

Does SQS guarantee message order?

Only FIFO queues do. FIFO queues keep strict order within each message group and provide exactly-once processing. Standard queues offer best-effort ordering and at-least-once delivery, so consumers must handle duplicates.
